# 输入文档更新流程

> 后续框架更新默认按本文档执行。目标是先把用户给的输入文档拆成可审、可追踪、可生成的框架文档，确认后再落到最终框架产物中。

## 标准流程

```text
输入文档
-> 拆解为框架草案
-> 用户确认
-> 落入 MD 参数契约与单系统沉淀
-> 修改最终数值文档并验算
-> 运行目标校验
-> 生成配置草案批次（仅在需要正式落配置时）
-> 用户按批次确认
-> 写入正式 Datas 并完成 Luban 导出与回执
```

正式配置阶段遵循 `02_AI规则/配置映射与正式落表流程.md`。数值方案确认不自动等于配置写入授权；在 `配置草案` 批次获得明确批准前，Vgame SVN 配置保持只读。

## 1. 接收输入文档

用户会提供需要修改模块的输入文档，可能是 Excel、Markdown、截图、策划说明或零散文本。

原始输入统一收纳到根目录 `_inputs/`，命名建议：

```text
YYYY-MM-DD_模块_主题_来源说明.ext
```

拆解后的框架草案不放 `_inputs/`，放到对应模块 `_reports/`，作为后续确认和追溯依据。

接收后先确认：

| 项目 | 要确认的内容 |
|---|---|
| 目标模块 | 战斗、养成、经济、节奏，或更细子模块 |
| 输入来源 | 用户新给文档、旧源表、正式配置、已有 v2 产物 |
| 修改性质 | 新增、替换、修正、补漏、口径裁决 |
| 是否落正式配置 | 默认不落正式配置，只更新框架；除非用户明确授权 |

## 2. 拆解为框架草案

不要直接把输入文档写进最终框架。先拆成一份可确认的框架草案，至少包含：

| 部分 | 内容 |
|---|---|
| 输入摘要 | 原文档讲了什么，哪些是规则，哪些是数值 |
| 字段拆解 | 应进入哪些参数列、生成列、说明列、追踪列 |
| 口径判断 | 哪些是新口径，哪些覆盖旧口径，哪些只是备注 |
| 影响范围 | 会影响哪些 MD 参数 ID、`04_数值文档`、脚本、验算和报告 |
| 待确认项 | 不确定、冲突、缺源、需要用户裁决的点 |
| 落地方案 | 预计新增/修改的文件清单和校验方式 |

草案可以先落在对应模块 `_reports/` 下，命名建议：

```text
P<阶段>_<模块>_<主题>_输入拆解.md
```

## 3. 用户确认门禁

在用户确认前，不把草案写入正式 MD 参数块、最终数值文档或生成器。

确认时至少要让用户看到：

- 会改哪些文件。
- 哪些字段会成为可调参数。
- 哪些内容只是人读说明。
- 哪些旧口径会被覆盖。
- 哪些内容仍保持待补或待正式配置接入。

## 4. 落入最终框架

用户确认后，再按模块规则落地：

| 类型 | 落地位置 |
|---|---|
| 可调输入 | `03_沉淀MD/参数基线/*.md` 的唯一机器参数块，或对应单系统沉淀 MD |
| 派生结果 | 对应 `生成_*.xlsx` |
| 生成逻辑 | 对应 `scripts/gen_*.py` 或同步脚本 |
| 最终文档 | `04_数值文档`；由本次生成物全量派生，不作为参数维护源 |
| 阅读入口 | 模块总览、阅读版、总览页或独立人读表 |
| 证据记录 | `_reports/*.md` |
| 全局状态 | 顶层 `README.md`、`_reports/00_总览_全量校验.md`、必要时 `汇总总览.xlsx` |

## 5. 校验与回报

局部设计验证至少运行目标模块脚本；只要要升级正式 `04`，必须运行完整 `run_all.py`、创建全新 staging、完成公式重算并通过动态验算后再发布。

回报格式：

```text
已落地：
校验结果：
待确认/未补：
未触碰范围：
```

## 原则

1. 输入文档先拆解、先确认，再落最终框架。
2. 不把不确定内容伪造成参数或结论。
3. 不直接覆盖正式配置，除非用户明确授权。
4. 生成器和报告必须能追溯到输入文档、旧源表或正式配置。
5. 工作区已有脏改时，优先只跑目标模块，避免重写无关产物。
6. `_shared/共享参数.xlsx` 与四模块 `参数.xlsx` 已删除；不得重新建立第二套 Excel 参数源。
7. 不从旧 `04` 回拷缺失文档；生成链缺项必须补生成器。
