# 数值文档工作流

> 适用于新增系统数值、旧系统大改、成长/经济/战斗/概率/奖励等需要沉淀并落到正式数值文档的任务。

## 单仓权威位置与运行入口

- 策划知识唯一入口：`knowledge-base/README.md`；数值正文子层：`knowledge-base/numerical/`。
- 数值生产源码、规则、源表与参数 MD：`numerical-workflows/v2/framework/`。
- 四份历史基础输入工作簿：`numerical-workflows/v2/legacy-inputs/`。
- 文件职责与哈希清单：`numerical-workflows/v2/workflow-manifest.json`。
- 全量生产：`python scripts/numerical-workflows/run_production.py`。
- 迁移/安全门禁：`python scripts/numerical-workflows/validate_migration.py`。
- 全部终稿、staging、动态验算及运行报告：`output/numerical-production-workflow-v2/`。

旧外部数值盘不再是生产依赖。`VGAME_CONFIG_DATAS` 仅提供真实项目配置的只读事实，任何正式配置写入都需要用户单独明确授权。房车执行 C；专武执行 B 的一个大版本兼容期，缺失专武源页时使用已沉淀的冻结兼容参数。

## 总原则

数值文档要分成三层主资料，并在最后追加验算与核算表：人工手改源表、AI 读写规则与 MD 参数沉淀、全量派生的最终数值文档、验算与核算表。

人工源表只服务“人怎么规划底层口径和全局规则”；AI 规则层服务“AI 怎么理解、扩展、校验”；输出文档服务“策划、程序、评审怎么读某个系统的最终结论”。三者不能混在一张表里，否则表会越来越能算、但越来越不好改。

验算与核算表不属于源表，也不属于策划阅读文档本身。它是最终校验产物，用来证明这版数值在预算、曲线、消耗、产出、战力和边界条件上是可追踪、可复核的。

任何数值任务都不直接从“给一版数值”跳到填正式表。必须先读完整案子、列出数值点、给出总体规划，再按模块和用户确认，形成可沉淀的 MD，最后再依据 MD 和源表生成或修改系统数值文档；只有当全局口径本身变化时，才修改人工源表。模块 `参数.xlsx` 不再是正式链路输入，参数与公式完整保存在 MD 中。

## 三层结构

### 1. 人工手改源表

定位：人手动维护的全局设计源和规划底座。

只保留核心内容和策划可读格式：

- 术语表、属性定义、属性分类、单位、百分比写法、ID 规则。
- 属性定价、道具定价、货币定价、投放系数、价值换算口径。
- 养成属性分配、成长投放预算、战力换算、模块属性占比。
- 经济、养成、节奏、战斗、奖励、概率等模块的通用规则和模板。
- 曲线使用少量控制参数或分段参数表达，不在源表里铺大量展开行，除非这些行本来就是策划需要手调的通用底座。
- 字段名、分组、备注必须让策划能直接读懂，不为了脚本方便加入过多中间列。
- 源表不承载 AI 的分析过程、临时假设、单系统生成明细、校验报告。

注意：

- 类似“房车养成”这样的单系统数值文档，不属于源表。
- 单系统文档应当由“对话确认记录 + 沉淀 MD + 人工源表”生成。
- 只有属性定价、道具定价、术语、养成属性分配等全局底座发生变化时，才回写源表。

要求：

- 人可以直接判断这一行为什么存在。
- AI 修改源表前，必须先说明要改哪些源表、哪些 sheet、哪些字段、为什么改。
- 未经确认，不把临时方案写入人工源表。

### 2. AI 读写规则与沉淀

定位：让 AI 知道如何读取、扩展、校验源表，并记录每次单系统设计判断。

需要沉淀的内容：

- 总体规划：项目数值边界、系统分层、战力口径、经济口径、节奏口径、属性定价、常用投放系数。
- 模块读写说明：经济、养成、节奏、战斗、奖励、概率等模块分别应该读哪些表、改哪些表、生成哪些输出。
- 表结构说明：sheet 用途、字段含义、ID 规则、引用关系、默认值、单位、百分比写法。
- 修改流程：每次修改前先读完整案子，列数值点，提出修改思路，和用户确认，再生成 MD 留档。
- 单系统沉淀：记录某个系统从需求、讨论、确认到最终数值文档的生成依据。
- 完整参数契约：稳定参数 ID、值、单位、公式、确定值、状态、适用范围、来源证据、下游终稿位置和变更记录。
- 校验规则：公式错误、缺字段、重复 ID、引用断链、预算超标、来源未定义、节奏不闭环等。

MD 是单系统参数与公式的唯一权威。需要机器读取时，在 MD 内使用带 schema 的 fenced JSON 参数块；不得另外维护一张模块参数 Excel 作为第二权威源。

AI 每次做数值时必须先输出：

1. 已阅读的输入来源。
2. 本次涉及的数值点。
3. 预计影响的模块和表。
4. 修改思路与待确认项。

用户确认后，AI 再写入 MD 留档，并按确认范围生成系统数值文档；如确认涉及全局底座变化，再修改人工源表或生成器。

### 3. 阅读输出文档

定位：依据源表证据与沉淀 MD 形成，给人阅读、评审和交接；不是参数维护源。

输出内容可以包括：

- 系统总览。
- 关键参数表。
- 曲线预览。
- 等级/阶段/节点明细。
- 消耗与产出汇总。
- 战力或价值预算。
- 风险项、待确认项、二期项。
- 与旧系统或目标模板的对照。

要求：

- 类似“房车养成”这样的单系统数值表，放在阅读输出层。
- 输出文档可以很完整，但参数修改必须先回到所属源表或 MD，再重新生成，不在终稿中形成第二套权威值。
- 生成器不得直接覆盖最终文档；重算结果先进入全新 staging，经动态验算后再整体发布。
- 输出文档要方便阅读，不追求把所有脚本中间字段展示出来。
- 读者不需要理解生成器，也能看懂本次数值结论。
- 最终文档不得依赖模块参数工作簿、外部链接、Power Query 或数据连接。

### 4. 验算与核算表

定位：最终校验产物，用来核对系统数值是否符合源表口径和沉淀 MD 的确认结果。

验算与核算表应当包含：

- 输入快照：本次读取了哪些源表、哪些 MD、哪些关键参数。
- 预算核算：属性预算、投放系数、等价价值、模块占比是否符合规划。
- 曲线验算：关键等级、关键阶段、满级、拐点、边界值是否正确。
- 消耗核算：单级消耗、阶段消耗、总消耗、材料分类、金币或通用货币消耗。
- 产出核算：材料来源、日/周产出、玩法来源、缺口、毕业周期。
- 战力核算：属性转战力、系统战力占比、实际生效比例。
- 异常检查：空值、重复 ID、引用断链、负数、异常百分比、超预算、来源未定义。
- 结论状态：通过、需确认、阻塞、历史遗留。

要求：

- 验算与核算表可以重算和覆盖，不作为手改源。
- 每个检查项要能回到源表字段、沉淀 MD 章节或生成器规则。
- 若用户只确认养成，不确认经济，则经济核算项要标记为“待经济模块确认”，不能假装闭环。

## 标准流程

1. 阅读完整案子
   - 读取用户给的策划案、Excel、历史数值文档、框架文档和相关功能说明。
   - 如果案子依赖旧系统，先读旧系统对应的数值结构和生成链路。
   - 只看单页或局部信息不足以进入落表阶段。

2. 列出数值点
   - 拆出所有会变成参数、曲线、公式、消耗、产出、概率、开放节奏、战力预算或校验项的点。
   - 区分“功能结构”“数值参数”“表现包装”“二期保留”“待用户确认”。
   - 明确哪些点进入全局、哪些点按角色/职业/队伍/玩法生效。

3. 先做规划和总览
   - 输出系统数值定位、模块分层、预算来源、属性归类、节奏口径、经济口径和验证口径。
   - 说明会影响哪些现有数值文档、生成器、经济账本、战力曲线或配置链。
   - 先给用户看，不直接落正式表。

4. 分模块和用户核对
   - 按模块逐个确认：属性投放、曲线、消耗、产出、概率、开放、边界和二期项。
   - 用户改口径时，先同步规划、数值点和 MD 参数契约，再继续下一模块。
   - 未确认模块不得默认为已批准落正式文档。

5. 生成 MD 留档
   - 在正式落表前生成 Markdown 留档，至少包含：
     - 输入来源
     - 数值点清单
     - 总览规划
     - 分模块确认记录
     - 默认假设
     - 待确认项
     - 风险和验证项
     - 后续落表范围
   - MD 文件路径要回报给用户，作为后续判断来源。

6. 生成系统数值产物，必要时更新源表、MD 与生成器
   - 只有在用户确认规划和模块口径后，才生成单系统数值文档、修改生成器或正式配置。
   - 如果本次确认的是全局底座变化，例如属性定价、道具定价、术语表、养成属性分配，才修改人工源表。
   - 如果本次确认的是单系统设计，例如房车养成，则先更新 MD，再生成系统数值产物，不新增模块参数 Excel。
   - 源表只写全局核心设计输入；展开明细、校验结果和阅读版报告进入输出层。
   - 落地后必须重算相关生成表，并跑目标校验。

7. 组装最终阅读版数值文档
   - 依据源表证据与 MD 参数契约，从本次生成物组装全新的 `04` staging；不得读取或回拷旧 `04`。
   - 标明来源、版本、日期、确认状态和未决项。
   - 如果全量校验有历史红项，要区分“本次新增引入”和“历史遗留”。
   - 检查终稿没有参数表外链、失效页签引用、数据连接或明显公式错误。

8. 动态验算并发布
   - 对 staging 做预算、曲线、消耗、产出、战力、文件集合、外链和公式错误校验。
   - 标明每个核算项的来源、结果、风险和待确认状态。
   - 验算未通过时不得替换正式 `04`；通过后整体发布，并对正式目录复验。

当前框架的标准发布命令顺序为：`sync_global_sources_to_md.py` → `run_all.py` → `stage_final_documents_from_md.py` → Excel 完整重算 → `validate_rebuild.py --target <staging>` → 发布 → 对正式 `04` 再次验算。

## 推荐目录口径

数值框架可以逐步整理为以下形态：

```text
框架v2/
  00_总览/
    总体规划.md
    数值边界与口径.md
    模块索引.md
  01_源表/
    术语表.xlsx
    属性定价.xlsx
    道具定价.xlsx
    养成属性分配.xlsx
    经济口径.xlsx
    节奏口径.xlsx
  02_AI规则/
    ai_readme.md
    表结构说明.md
    模块读写规则.md
    schema/
  03_沉淀MD/
    养成/
      房车养成系统数值设计文档-2026-07-03.md
  04_数值文档/
    养成/
      房车养成_数值文档.xlsx
      房车养成_阅读版.md
  05_验算核算/
    养成/
      房车养成_验算核算.xlsx
      房车养成_验算核算.md
  养成/
    scripts/               # 生成器与校验
  经济/
    scripts/
  节奏/
    scripts/
```

这只是目标形态，不要求一次性重构。后续每个模块改动时，按本流程逐步迁移。

## 输出门禁

| 阶段 | 必须输出 | 是否可改正式数值 |
|---|---|---|
| 阅读案子 | 输入来源与理解摘要 | 否 |
| 数值点拆解 | 数值点清单、待确认项 | 否 |
| 规划总览 | 总览方案、影响范围 | 否 |
| 模块核对 | 每个模块确认记录 | 否 |
| MD 留档 | 可追踪 Markdown 文档 | 否 |
| 系统文档生成 | 单系统生成物、生成表、校验报告 | 否；先进入 staging |
| 源表更新 | 属性定价、道具定价、术语表、养成属性分配等全局源表 | 是，需用户确认 |
| 最终数值文档 | 面向评审与交接的派生文档 | 否；修改源表/MD 后全量重建 |
| 验算核算 | 预算、曲线、消耗、产出、战力、异常检查表 | 是，派生输出 |

## 常见提醒

- “基础属性”“基础属性百分比”“二级属性”必须拆开说，不能混写。
- 全局属性、职业属性、角色个人属性、装备属性必须分层。
- 经济消耗不能只给总量，要说明材料来源是否已定。
- 战力预算不能只看满级，还要说明曲线进度和实际吃到的比例。
- 任何临时假设都要进 MD 的“待确认项”或“默认假设”，不能藏在生成器里。
