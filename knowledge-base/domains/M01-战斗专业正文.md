## 0. 阅读约定与来源标签

| provenance / 状态 | 含义 |
|---|---|
| `SOURCE_EXPLICIT` | 来自已确认 Design、数值沉淀、正式决议等原文明示内容；不代表已配置或已上线 |
| `WORKING_COPY_OBSERVED` | 本机 SVN 工作副本中观察到的表、代码或资源；不证明 Production/LIVE，也不等于正式策划口径 |
| `CROSS_SOURCE_SYNTHESIS` | 由多份证据组织出的流程、边界或关系；需评审确认，不得伪装成原文结论 |
| `DESIGN_PROPOSAL` | 为补齐缺口提出的候选方案，非项目既有事实 |
| `UNKNOWN` | 无法可靠判断；不得代填最可能答案 |
| `UNKNOWN_LIVE` | 工程实现链存在，但缺集中版本—开关—发布时间台账，不能盖为 LIVE |
| `GAP` | 已确认职责适用，但策划规则、实现或文档缺失 |
| `P0_CONFLICT` / `P1_GAP` | 高优先级冲突或缺口 |

> **全局基调**：战斗域 8 个系统正文（SYS-IN-01..08）目标设计轴普遍为 `WORKING_COPY_OBSERVED_DESIGN_GAP`——实现链存在，但**绝大多数规则无权威目标设计冻结**，引用的共享契约（CONTRACT-BATTLE-RESULT / CONTRACT-FAILURE-IDEMPOTENCY 等）均为 `FRAMEWORK_CONTRACT`（去重/路由契约，不构成口径权威）。运行状态轴整体为 `UNKNOWN_LIVE`（缺集中版本—开关—发布时间台账）。

## 1. 战斗规则（CB-R01..R08）

### 1.1 实例与胜负（CB-R01）

**现状**：战斗实例是全部战斗玩法的运行时容器，接收玩法/关卡/编队快照 → 加载战斗世界 → 驱动开始/暂停/结束 → 交回确定性战斗结果。

| 子主题 | 现状要点 | 来源 | 状态 |
|---|---|---|---|
| 上下文生命周期 | `BattleContext.lua` 每次战斗 new，退出销毁；`BattleSystem.lua` Init/Destroy 实现；承载 currentIntent/intentType/levelId/battleId/isFirstPass/isQuickBattle | SYS-IN-01-R01 | `WORKING_COPY_OBSERVED`（目标口径 `GAP`） |
| 进入防重入与超时 | 三标志防重入 + 双 notify 防护 + 30 秒超时（代码常量，未见策划冻结） | SYS-IN-01-R02/EX01 | `WORKING_COPY_OBSERVED`；30 秒阈值 `P1_GAP` |
| 世界加载与过渡 | intentType 分发 Start/Next/Repeat/SpecificLevel/Continue；QuickBattle 走本地纯逻辑不进战斗 View | SYS-IN-01-R03 | `WORKING_COPY_OBSERVED` |
| 非战斗关卡直通 | LevelType_Chest/Chat/Fish/KeyPuzzleUnlock/CircuitConnect/Question 跳过战斗世界，以胜利直通结算 | SYS-IN-01-R04/C02 | `WORKING_COPY_OBSERVED` |
| 结束判定与确定性结果 | `DoGameOver` 幂等守卫 → `CReqFightOver`（LevelID/BattleID/BattleResult）；BattleRecord/ResultHash/Version **仅在 GameModeBase.GenerateBattleResult 且 MessageProcessor 为 NormalMessageProcessor 时赋值**，PVPVEMode 重写后不赋这三字段 | SYS-IN-01-R05 | `WORKING_COPY_OBSERVED` |
| 暂停与结算触发 | `SetGameOver`/`PauseGame("GameOver")`/关 UIBattleView → 按 LevelType 路由 WinSettlementUI/LoseSettlementUI；PVPVE 有独立结算协议 | SYS-IN-01-R06 | `WORKING_COPY_OBSERVED` |
| 异常退出与续局 | `RebuildLastBattle` 依据 `ResumableBattleDataHeader` 重建；`OnReconnectServer` 为空实现；断线/顶号/失败扣成本、重复结算防护无冻结口径 | SYS-IN-01-R07/EX03 | `DESIGN_GAP` / `P0_GAP` |

**胜负判定多入口（重要）**：不存在单一 `DoGameOver` 唯一结算入口，实际有四个触发点：①`BaseGameMode.DoGameOver`（幂等保护，分发 OnWin/OnLose）；②`World.SetGameOver`（PVPVE、GameOverData 关卡触发、技能失败、玩家死亡等直接调用）；③`PVPMode.OnLose` 内联结算；④`GameOverData` 触发器。来源 SYS-IN-06-R08 / SYS-IN-08-R01/C01，`WORKING_COPY_OBSERVED`。

**GAP / UNKNOWN**：
- `SYS-IN-01-Q01`（P0）：失败、断线重连、主动退出、顶号、进程重启的完整状态回滚与结算幂等口径。`OnReconnectServer` 空实现，顶号可能丢结算。
- `SYS-IN-01-Q02`（P1）：30 秒超时阈值是否正式冻结。
- **战斗总纲未批准**：`20-战斗框架.md §6` 明确「缺少一份已批准的正式战斗总纲」；多数现有战斗 Design 是反推 Draft。`GAP`。

**证据**：SYS-IN-01-EV01..EV06（BattleContext.lua / BattleSystem.lua / GameModeBase.cs / NormalMode.cs / LLevelMgr.cs / combat-domain-audit.md）。

## 4. 胜负与结算（SYS-IN-08 / SYS-IN-06 + 共享契约）

> 本节从 SYS-IN-08、SYS-IN-06 与共享契约 CONTRACT-BATTLE-RESULT、CONTRACT-REWARD-SETTLEMENT、CONTRACT-FAILURE-IDEMPOTENCY 整理。**这些契约均为 `FRAMEWORK_CONTRACT`（CROSS_SOURCE_SYNTHESIS），是去重/路由契约，不构成口径权威。**

### 4.1 胜负判定

**现状**（SYS-IN-08-R01/C01，`WORKING_COPY_OBSERVED`）：
- 胜负不存在单一入口，四个触发点：①`BaseGameMode.DoGameOver`（IsGameOver 幂等保护，分发 OnWin/OnLose）；②`World.SetGameOver`（总调度）；③`PVPMode.OnLose` 内联结算；④`GameOverData` 触发器。
- `ResultHash`/`Version`/`BattleRecord` 仅在 `GameModeBase.GenerateBattleResult` 且 MessageProcessor 为 `NormalMessageProcessor` 时赋值；`PVPVEMode` 重写后这三字段缺失（仅算 hash 打日志）。

**CONTRACT-BATTLE-RESULT**（`FRAMEWORK_CONTRACT`）：统一表达战斗胜负、评价条件、战利品触发和系统侧结果消费。被 SYS-IN-01-R05/R06、SYS-IN-06-R03/R08、SYS-IN-08-R01/R04、SYS-OUT-GP-09-R04 引用。**不构成口径权威**。

### 4.2 结果上报与结算触发链

**现状**（SYS-IN-08-F01/R03，`WORKING_COPY_OBSERVED`）：
1. 判定胜负 → 2. GenerateBattleResult 组装 BattleResult/CollectData → 3. OnWin/OnLose 经 Visual.VMsg_GameOver 交表现层，CReqFightOver 上报服务器 → 4. 服务器 CNotifyFightOver 下发，BattleSystem:CRespNotifyFightOver 暂停战斗、关 UIBattleView、按 LevelType 路由结算界面（**通用回调不覆盖 PVPVE**：竞技场不走 CNotifyFightOver 通用链，使用专用 ReqBattleResult/RespBattleResult 对账，见 §3.2 竞技场行） → 5. 上报下游（真实入账 SYS-OUT-SU-05、任务 SYS-OUT-SU-07、玩法进度 SYS-OUT-GP-*；下游直接消费调用链未见客户端证据，SYS-IN-08-Q06=UNKNOWN）。

**结算 UI 路由**（SYS-IN-08-C03）：按 LevelType 读取 WinSettlementUI/LoseSettlementUI（保底 UICommonSettlementView/UIResourceLevelSettlementFail）；BossDungeonChallenges_Hard 走 BossDungeonSystem、PVP/PVP_BOSS 走 TowerSystem 专用结算。

### 4.3 评价条件

**现状**（SYS-IN-08-R04/C02，`WORKING_COPY_OBSERVED_NEEDS_DESIGN_CONFIRMATION`）：
- 单关评价以 LevelCondition 1/2/3 为结算输入（当前：①战斗胜利 ②战败角色不超过1个 ③通关时队伍血量全部高于30%），由 SYS-OUT-GP-01 已核。
- 星级聚合与章节奖励由 SYS-OUT-GP-01 维护，本系统只作输入。
- `SYS-IN-08-Q03`（P1）：LevelCondition 1/2/3 是否就是正式单关评价规则，运行时消费方是谁？

### 4.4 奖励结算分权

**现状**（SYS-IN-08-R05，`CURRENT_DESIGN_IDENTITY`）：
- 战斗实例只上报结果、UI 只展示奖励、SYS-IN-08 只记录战利品与触发结算。
- **发多少、发什么与真实入账归 SYS-OUT-SU-05**（掉落与奖励）。
- 视觉掉落、战利品记录、真实入账三层分权（SYS-IN-07-R04 / SYS-IN-08-R05）。

**CONTRACT-REWARD-SETTLEMENT**（`FRAMEWORK_CONTRACT`）：统一区分首通、重复、周期、排行、展示预览和真实入账。被 SYS-IN-08-R05 引用。**不构成口径权威**。

### 4.5 幂等与失败恢复

**现状**（SYS-IN-08-EX01/EX04，SYS-IN-01-EX03）：
- `DoGameOver` 的 `IsGameOver` 保护阻止重复进入结果生成（`WORKING_COPY_OBSERVED`）。
- **断线重连与重复请求的补发口径仍待冻结**（`P1_GAP`）。
- `OnReconnectServer` 为空实现；顶号时 CRespNotifyFightOver 若 battleContext 为空直接返回，可能丢结算（`P0_GAP`）。
- 失败是否扣成本、断线重连是否继续、超时是否统一判负，各玩法口径未冻结（SYS-IN-06-EX03）。

**CONTRACT-FAILURE-STATE**（`FRAMEWORK_CONTRACT`）：表达单位死亡、全员死亡、战斗失败与失败结果触发；不包含重试、补发或防重复入账。**CONTRACT-FAILURE-IDEMPOTENCY**（`FRAMEWORK_CONTRACT`）仅表达断线重连、异常退出、加载失败、重复请求、补发、回滚和防重复入账。二者均不构成口径权威，单纯的死亡/失败状态不得被路由到幂等契约。

### 4.6 金币带出口径冲突（P0）

**现状**（SYS-IN-08-R07/EX02/C04，`P0_CONFLICT`）：
- Draft 规则（`局内金币带出Design Doc.md`）定义 CarryOutRatio/CarryOutMaxGold/MaxInnerGold 与扫荡补发。
- 工作副本 LevelType 含 `GoldCarryOutEnable`、UIlevel 含 `CarryOutRatio`/`CarryOutMaxGold`（字段已落表）。
- 但**服务器结算消费链未核到**，客户端 C#/Lua 侧仅在配置生成层（UILevelDataModel.cs / ExcelDataDefine.lua）携带字段，未核到结算消费方。
- 三方不一致（Draft 规则 / 工作副本字段 / 未核到的服务器消费链），`SYS-IN-08-Q01`（P0）待裁决。**不选边，不当作已上线口径**。
