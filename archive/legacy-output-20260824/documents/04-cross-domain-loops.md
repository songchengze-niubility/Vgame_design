# Vgame 项目级跨域闭环与责任矩阵

> 本文件把知识树变成可执行的项目接口。玩家系统一级只分战斗内（BI）与战斗外（BO）；XS 只提供跨域支撑，不拥有玩家系统身份。

## 1. 两域接口契约

| 接口 | 战斗外负责 | 战斗内负责 | 共同验收结果 |
|---|---|---|---|
| 进入战斗 | 入口、开放、次数、成本、编队、玩法上下文 | 校验并加载 GameMode、关卡、单位和规则 | 合法请求进入正确实例；非法请求有明确反馈 |
| 战前构筑 | 角色拥有、等级、星级、收容物/旅券/映射装备等最终构筑 | 消费冻结后的战斗属性、技能与队伍数据 | 同一快照可复现；属性来源可追踪 |
| 玩法规则 | 周期、层级、赛季、匹配、排行榜、奖励 | 地形、波次、敌人、时限、胜负和实时机制 | 外壳与实例使用同一玩法身份和版本 |
| 战斗结果 | 接收并持久化胜负、评价、最高层、排名输入和任务事件 | 产生确定性结果、战斗统计与结算触发 | 重连、重复提交、超时和异常结果可处理 |
| 奖励经济 | 决定首通/重复/概率/周期奖励并实际入账 | 只产生可结算事件与视觉反馈 | 视觉掉落不改变真实奖励；账本守恒 |
| 教学与信息 | 管系统开放、入口教学、页面和回流提示 | 管 HUD、操作教学、预警、命中/受击和失败原因 | 玩家知道为何可玩、如何玩、为何胜负 |

## 2. 六条项目级闭环

### L-01 新玩家建立循环

`注册/建角 → 主线入口 → 战斗教学 → 首次结算 → 主角等级/系统开放 → 第一次养成 → 再次挑战`

- 主域：BO-08、BO-01、BI-08、BI-09、BO-02。
- 必须验证：开放顺序、教学完成、首通奖励、第一次成长可见变化、断点恢复。
- 当前缺口：完整的新手流程覆盖矩阵和版本化流失漏斗。

### L-02 核心成长循环

`选择验证玩法 → 编队与构筑 → 战斗 → 掉落/结算 → 资源入账 → 养成选择 → 属性/机制变化 → 回到验证玩法`

- 主域：BO-01、BO-02、BO-04、BI-02、BI-06、BI-07。
- 必须验证：资源来源/消耗、成长转化、同投入对比、下一目标可理解。
- 当前缺口：现行收容物接入后的玩家终态曲线，以及专武迁移裁决。

### L-03 日周留存循环

`登录 → 可领取/任务提示 → 日常/周常/资源本 → 活跃与任务推进 → 商店/养成消费 → 次日/次周目标`

- 主域：BO-05、BO-04、BO-01、BO-10、BO-09。
- 必须验证：周期重置、补领、上限、重复奖励、红点、跨时区和版本切换。
- 当前缺口：通行证当前关闭口径与正式文档身份的同步。

### L-04 阵容获取与商业化循环

`需求暴露 → 角色/收容物展示 → 卡池/商店/月卡/礼包 → 获得与重复转化 → 阵容扩展/成长 → 战斗验证`

- 主域：BO-03、BO-06、BO-04、BO-02、BI-02。
- 必须验证：概率与保底、货币扣除、重复转化、价值展示、公平性和退款/异常。
- 当前缺口：专武卡池废弃与收容物替代的单一 canonical 规则。

### L-05 赛季与 LiveOps 循环

`版本范围 → 活动/赛季开放 → 参与与挑战 → 排名/进度 → 周期结算 → 奖励/补偿 → 重置/关闭 → 数据复盘`

- 主域：BO-09、BO-01、BO-05、BO-04、XS-05、XS-06。
- 责任拆分：BO-09 定义玩家可见内容与周期；XS-05 定义指标、埋点与实验判定；XS-06 负责开关、实验分流部署、灰度、Hotfix、发布和回滚。
- 必须验证：功能开关、灰度、跨版本兼容、赛季重置、邮件补偿、回滚和数据监控。
- 当前缺口：集中式版本/活动/AB/灰度/Hotfix 真实台账。

### L-06 内容生产与事实回写循环

`Design → Proposal → Task → Excel/编辑器/代码 → 生成与序列化 → QA/实机 → 发布 → 数据/问题 → 文档与图谱回写`

- 主域：XS-02、XS-03、XS-06、XS-07，覆盖 BI 与 BO。
- 必须验证：权威源、生成目标、引用完整性、变更影响、回归结果和废弃记录。
- 当前事实：服务端 JSON 当前目标为 `Config/GameConfig/server/json`；旧 `server_json` 口径已漂移。

## 3. 玩法双域责任模板

任何主线、副本、竞技场、爬塔或赛季玩法都必须同时填写以下两列，不能把整套玩法只塞进一侧。

| 战斗外壳层（BO-01 主责） | 战斗内实例（BI-05/06 主责） |
|---|---|
| 入口与 UI | SceneData / LogicData |
| 解锁与开放时间 | GameMode / Intent |
| 体力、门票、次数 | 地形、移动与镜头 |
| 编队与助战 | 波次、刷怪与 Boss 阶段 |
| 难度档、层级、赛季 | 实时 Buff、技能与环境规则 |
| 扫荡、匹配、排名 | 时限、目标、胜负条件 |
| 首通、复刷、周期奖励 | 结果、统计与结算触发 |
| 重置、补领、关闭、回滚 | 断线、暂停、重连与异常结束 |

项目级实现追踪应继续落成：

`正式玩法 → LevelType → Intent → GameMode → SceneData → 胜负/结算 → Drop/任务/排名`

## 5. 责任边界

- 系统 Owner 对规则、状态和验收负责。
- 数值 Owner 对参数源、模型假设、账本与验证区间负责。
- 配置 Owner 对真实源表、引用、导出与生成物一致性负责。
- 程序 Owner 对运行时消费、兼容、异常和可观测性负责。
- UI/UX Owner 对入口、信息、反馈和错误恢复负责。
- QA/发布 Owner 对用例、回归、版本范围、灰度与回滚负责。
- 知识维护者不替上述角色做业务裁决，只记录证据、冲突、替代链和最后回源日期。

战斗难度同样分责：BI-07 决定具体玩法的目标、基准场景与验收阈值；XS-01 维护共享公式、玩家/怪物基线、生成器和仿真版本。

框架的合格标准不是“每个目录都有文件”，而是每条关键闭环都能从规则追到配置/实现，再从实机结果回到设计。
